## 2. The native engine (`src/native.rs`)

The largest group, and the one most worth a reviewer's time.

**The design.** Functions that qualify are compiled with Cranelift. Generated code
handles Int and Bool as `i64` directly, with every arithmetic operation checked for
overflow; every other value lives in an arena (`Vec<Option<Value>>`) inside a `Ctx`,
and generated code holds it only as an `i64` handle. Generated code never
dereferences a value: every operation on a non-Int value calls a Rust helper
(`rt_*`), which calls the interpreter's own function for it. So the memory that
generated code reads and writes directly is the `Ctx` header (steps, depth, the
`failed` flag, at fixed offsets) and the argument arrays it builds on its own stack.

**The contract.** Each `rt_*` helper is an `unsafe extern "C" fn` taking `*mut Ctx`.
Its `# Safety` section states that the pointer must be the `Ctx` of the native call
now running, which `Native::call` (or `staal_aot_main` in an executable) creates,
keeps alive and exclusively borrows for the whole call. The pointer is turned into a
reference once, by `ctx`. Helpers that take arguments also take `argv` and `n`, and
require `argv` to point to `n` readable `i64`s; generated code passes a stack array
of exactly that length (`take_args`).

**What makes a wrong handle harmless.** A handle is checked on every use (`slot`):
out of range, zero, negative or already taken is an `Internal` failure, never an
out-of-bounds read. So a code generation mistake about handles becomes a failed run,
not memory corruption.

**What it relies on.** That Cranelift generates the code it is asked to; that the
generated code passes the pointers the contract states (checked by running every
runtime case on both engines and comparing results, logs and journals:
`engines_test.rs`, `aot_test.rs`; 27 deliberate faults in the native compiler each
caught, [GUIDE.md](../GUIDE.md) "Native code and the C interface"); and that the
module's code is not freed while a function from it runs (`Drop` for the module).

**A panic inside a helper.** A helper's body returns failures as values, so a panic
is a bug. If one happens, it cannot unwind through the `extern "C"` frame: since Rust
1.81 that aborts the process. This is memory safe; the run stops, and its journal
lets it be resumed.

## 3. The C interface and its callers

`src/capi.rs`: every exported function that takes a pointer (all but `staal_version`) is an
`unsafe extern "C" fn` whose
contract (in `include/staal.h` and its `# Safety` section) is that each argument is
NULL where allowed or a NUL-terminated string valid for the call. `arg` reads each
one, refusing NULL where it is not allowed and non-UTF-8 text, and the body runs under
`catch_unwind`, so a panic becomes an `error` result rather than unwinding into C.
Every returned string comes from `CString::into_raw` and is released only by
`staal_free`, which takes it back with `CString::from_raw`.

The callers: the Python package (`python/staal/__init__.py`) declares each return type
`c_void_p` so ctypes never copies and loses the pointer, reads the string and frees
it once; the Node.js addon (`node/src/lib.rs`, four items in the table) does the same
in Rust.

What a reviewer might check: that no path returns a pointer not made by
`CString::into_raw`, and that the bindings free each result exactly once on every
path, including exceptions.
